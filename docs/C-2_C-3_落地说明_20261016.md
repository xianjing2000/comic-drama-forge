## C-2　分镜首建接入 `kind="storyboard"` 教训召回

### 改了什么

- 文件：`app/storyboard_helpers.py`，函数 `_prep_shot`，**新增块在 `:2451-2470`**（紧跟 `_prompt_preflight` 调用之后、过渡镜注入之前）。

```python
try:
    _sb_learned = prompt_memory.learned_prompt(
        kind="storyboard", prompt=prompt, project=project_name,
        root_dir=PROJECT_OUTPUT_DIR, max_hints=1,
        style=_qc_style_of(project_name))
    if _sb_learned and _sb_learned != prompt:
        prompt = _sb_learned
        logger.info("分镜首建召回 storyboard 教训：shot=%s", shot_p.get("shot_id"))
except Exception as _lm_e:  # fail-open
    logger.warning("分镜首建 storyboard 教训召回失败（忽略）：%s", _lm_e)
```

### 为什么这么放（设计依据）

- **根因**：此前首建只经 `_prompt_preflight` 召回 `kind="prompt"`（预检教训）；`kind="storyboard"`（质检缺陷教训：面板雷同/景别/发型…）**只在 `attempt>0` 的重试轮**（`:2904-2940`）与软放行后记账时召回 → 每个新镜头首建**必然不复用**已沉淀缺陷教训。
- **位置选在预检之后**：不改预检语义、不改 `orig_prompt` 指纹键（`:2442` 的注释纪律：教训库指纹以构建器输出为准）；读的是预检自愈后的提示词，与重试轮的 `_retry_base` **同口径**（键一致才不会把同一缺陷记成两条）。
- **`max_hints=1`**：与重试轮一致——教训是「上次失败的具体缺陷描述」，越注越长的提示词与 H3 官方 Simple-and-Clear 相悖。
- **fail-open**：`prompt_memory` / `PROJECT_OUTPUT_DIR` / `_qc_style_of` 均为**模块级导入**（`:100` / `:9` / `:48`），故正常路径可用；任何异常都被 `except` 兜住 → 绝不因记忆模块出问题而卡住整集生产。
- `learned_prompt` 只**在末尾追加** `【历史质检修正建议（请务必遵守）】` 段，无教训时**原样返回** → 新项目/无教训时为 no-op，零副作用。

### 影响面

- **缓存键**：注入教训会改变提示词 → 改内容寻址缓存键（路线图红线 #2）。**仅在「该项目已有 storyboard 教训」时**才发生变化；无教训项目完全无感。首次生效会有一轮重算，不影响产物续跑。
- **多副本**：这是 `app/` 代码 → **必须同步四处副本**（见下）。

### 落地 runbook（需你执行）

1. （可选）看同步计划：`python tools/sync_copies.py`（默认 dry-run，只打印计划）。
   - ⚠️ 注意：目前源与 `_backend` 副本**存在漂移**（源较新），同步会一并把 `_backend` 追平——建议先 dry-run 看清单再决定。
2. 执行同步：`python tools/sync_copies.py --apply`（4 处副本按源统一；运行镜像才是真正加载的那份）。
3. 重启后端（带 `APP_PORT=5211` 与 `MJSCXT_DATA_DIR=<APPDATA>\mjscxt-desktop\mjscxt-data`）。
4. 生效判据：进程启动时间 > 镜像文件 mtime。

### 验证

- 对一个**已有历史教训**的项目跑 1 镜首建，日志应出现 `分镜首建召回 storyboard 教训：shot=…`。
- 对**无教训**项目跑 1 镜，日志**不应**出现该行，且提示词与改前一致（no-op 验证）。
- 回退：删除 `:2451-2470` 新增块即可（纯增量）。

## C-3　分镜多样性离线守卫（面板雷同量化）

### 是什么

- 新文件：`tools/verify_storyboard_diversity.py`（**不在 `app/` 下 → 不需要副本同步**）。
- 对同一目录（=同一集/场）内的分镜图两两做 **dHash 感知哈希**，把「几乎一模一样的两张」显式列出；可选跨目录比对。**不依赖任何模型、不依赖人工看片、不导入 `app.config`**（无导入期副作用）。

### 为什么

分镜质检是 VLM「判官」，实测会抖（同一张图 45~92 分），缺陷榜首是 **「面板雷同 573 次」**。本工具提供确定性交叉核对：把主观的「雷同」变成可量化、可复核的汉明距离。

### 用法

```bat
python tools/verify_storyboard_diversity.py --root "<STORYBOARDS_DIR>\<项目>" 
python tools/verify_storyboard_diversity.py --root "<...>\ep01" --max-distance 6 --strict
python tools/verify_storyboard_diversity.py --root "<...>" --cross --json
```

- 依赖：**Pillow + numpy**（本仓库 requirements 已有）。
- 退出码：`0`=达标/报告模式；`1`=有超阈值近重复（仅 `--strict`）；`2`=用法/环境错误。
- `--max-distance` 默认 `6`（dHash 64 位汉明距离，≈ ≥90% 相似视为近重复）。
- 可选：运行环境若装了 `insightface`+`cv2`，会自动追加**人脸余弦一致性**；未装则静默跳过（本仓库 requirements 未含，故默认只做感知哈希）。

### 建议接入

- 作为**离线门禁**：对刚跑完的一集跑 `--strict`，非 0 即人工复核那几对（比 VLM 分数更可复核）。
- 可作为 CI/发布前检查（`--json` 出结构化结果）。

### 验证

- 在一个**已知有雷同镜**的集上跑，应列出对应 `d=…` 对；在一个正常集上跑，近重复应≈0。
- 回退：删文件即可（纯新增）。
