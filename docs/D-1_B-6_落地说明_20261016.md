## D-1　拆服务定位器（已完成）

### 做了什么：把「服务定位器」换成「显式依赖」（两次推进，最终**全量删除 `_A()`**）
- **第一步（先做，低风险）**：`pipeline._A()` / `autopilot._A()` 曾先改为返回**显式依赖命名空间**
  （`types.SimpleNamespace`），删 `sys.modules.get("app")`，调用点零改动。
- **第二步（本轮收尾，已全量删除 `_A()`）**：用一次性脚本把这 **~48 个函数里的 `A = _A()` + `A.X`
  全部机械改写为函数内显式 import**（`A.X` → `X`；`getattr(A, "X", D)` → `X`），并删除
  `_A()` 定义本身。动态 `getattr(A, <var>)` 的三处改为显式映射：
  - `_run_task_worker`：`registry/lock` 由 `job_state` 的显式字典映射；
  - `probe_assets`：`dir_key` → `{CHARACTERS_DIR,ITEMS_DIR,SCENES_DIR}` 字典；
  - 另 `deliverable_path` 补 `from config import PROJECT_OUTPUT_DIR`。
- 其它去耦合点：`routes/autopilot._live_snapshot` → `from job_state import generation_state`；
  `boot_qc_migration` 下沉 `qc_helpers`（serve/app 改 import/再导出）；autopilot 里恒为 None 的
  `getattr(_A(), "schedule_cancel", None)` → 直接 `None`。

### 为什么分两步
一步到位把 87 处 `A.X` 盲改风险过高（一处映射错＝整条流水线崩）。第一步「换实现、调用点不动」
先把服务定位器去掉并验证通过；第二步在**有了 VM bash 可跑 pyflakes/compileall** 之后，用脚本
机械改写、逐轮验证，才安全落地。符号来源始终由 **app.py 的实际 import 锚定**。

### 验收（已在本机 VM 实跑）

- `grep` 实证：`app/` 里 **`_A()` 定义与 `A.X` 用法均已归零**（仅注释/文档字符串里留历史说明）。
- `tests/test_app_attr_bindings.py` 已改写为「校验显式依赖 import 可解析」，**通过**。
  （此前那条检测 `A.X` 命名空间版本的中间态测试，曾当场抓出漏项 `A.style_kit`。）

## B-6　单元级续跑（核验：**已实质达成，无需改动**）

原计划称「自动失败重试仍整步级、崩一次整集重跑」。核验 `app/pipeline.py` 后发现**每个步骤入口
都先探测已完成即跳过**：

| 步骤 | 入口探测 |
|---|---|
| `step_script` (`:1589`) | `probe_script(ctx) and not overwrite_script → skipped` |
| `step_assets` (`:1827`) | `probe_assets(ctx).done → skipped`；且只把 **missing 名单**传给 worker（S13 断点续跑） |
| `step_storyboard` (`:1877`) | `probe_storyboard(ctx).done → skipped`；worker 内跳过已达标镜 |
| `step_video` (`:1949`) | `probe_video(ctx).done → skipped`；按场复用（`needs_scene_rerun` 只重画坏场） |
| `step_upscale` (`:2371`) / `step_final` (`:2032`) | 同样 `probe_X.done → skipped` |

因此「重试一次整步」的**有效粒度已经是镜/场/段**：已完成单元被 probe/checkpoint 跳过，不重烧 GPU。
**结论**：B-6 无需新增「步内单元重试循环」——那与既有 probe/checkpoint 重复，反而增加复杂度与回归面。
真正值得做的是据 **A-3 阶段耗时数据**判断是否还有整步级的**非单元**开销（如脚本重写），那属独立议题。
