### 4.2 To-Be：职责边界（三层，各司其职）

| 层 | 模块 | 职责（一句话） | 落盘策略 |
|---|---|---|---|
| **真相层（持久化）** | task_store（既有 SQLite）+ comfyui_job_store（既有）+ **新 runtime_state.py** | 「发生了什么」的唯一事实来源：任务生命周期、单元完成、远端 prompt 归属、托管调度游标 | 每次状态跃迁**同步**写（SQLite 事务 / 原子 JSON） |
| **进度层（内存热缓存）** | job_state.generation_state（保留） | 「现在怎么样」的高频读缓存，供前端轮询，**只由真相层写入** | 不直接落盘；但有 write-through（见 4.3） |
| **调度层（内存 + 小状态）** | autopilot._STATE | 守护线程自己的循环控制（running / paused / current / next） | 只落**决策所需最小集**：paused / pause_reason + current + last_run + _LAST_RUN（改由 runtime_state 读写） |

**铁律**：
1. generation_state 的**唯一写入口**是 job_state.update(task_id, **kw)（内部同步 task_store.mark_unit / set_progress），消灭 82 处裸下标写；
2. 任何跨重启需要「知道进度」的地方，**只读真相层**，不许读内存态；
3. _LAST_RUN（防空转间隔，autopilot.py:170 / MIN_RERUN_INTERVAL=45）必须落盘 —— 现在纯内存，**重启即清零**，正是「重启后重复烧 GPU」的直接来源之一。

### 4.3 「重启后状态一致」的启动协议（Reconcile）

启动时序（在 serve.py / app.py 现有启动点之后插入一步**对账**）：

    ① 载入配置与路径（config.init_paths / paths.init_root）
    ② task_store.recycle_interrupted()          # 既有：running → interrupted
    ③ 【新】reconcile_startup()：
         for task in task_store.list(status=interrupted):
             units_done = task_store.done_units(task.id)
             artifacts  = probe_artifacts(task)        # 按 kind 探测产物（分镜图 / 成片场次 / 超分）
             若 artifacts 已齐 → 直接标 done（崩溃前其实已完成，零 GPU）
             否则 → 标 interrupted_resumable，resume_cursor = 第一个缺失单元
             同时把结果写进 generation_state[task.id]（前端进度不归零）
    ④ 【新】autopilot.restore_schedule()：
         恢复 paused / pause_reason（既有）
         + 从 runtime_state 恢复 current / last_run / _LAST_RUN（新增）
         + 若 last_run 的集在 task_store 里是 interrupted_resumable → 优先续跑该集，不重挑下一集
    ⑤ 启动守护线程（既有）

**关键设计决定（三条，都是为了「不重复烧 GPU」）**

1. **完成判据 = 产物，不是标志位**（复用既有先例）：task_store.is_unit_done(result_path)（:330）、video_helpers.py:1675 的逐场复用、comfyui_job_store 的哈希复用。启动对账统一调用同一判据函数，避免多套「算不算完成」的口径。
2. **interrupted_tasks 从计数改为清单**（T12 §4.2 S3）：recycle_interrupted() 返回 [{task_id, project, kind, progress, done_units, missing_units, resumable}]；routes/status_api.py:89 相应改为返回数组（前端兼容：同时保留 interrupted_tasks_count）。
3. **暂停语义作用域收窄**（T12 §4.2 S4）：pipeline.py:2158 cancellation.clear() 会清掉**先进集次**的停止判定器。改为取消 clear()、只用 push(token) / reset(token)（cancellation.py:52/59 已具备），clear() 降级为测试专用。当前由「集级锁 + 单实例锁」挡住（pipeline.py:2127），一旦放开多集并行会静默失效。

### 4.4 「重启后重复烧 GPU」的四条来源与逐条封堵

| # | 来源 | 证据 | 封堵 |
|---|---|---|---|
| 1 | 托管重启后重挑一集重跑（attempts 与 current 口径不一致 → _pick_next 再试一次） | autopilot.py:315-337（只落 paused）+ :1227-1240（读 _attempts_get）+ T12 §4.2 S2 | runtime_state 落 current / last_run；启动对账优先续跑 |
| 2 | 防空转间隔失效（_LAST_RUN 纯内存 → 重启后立刻可重跑同一集） | autopilot.py:170、:1243-1248 | _LAST_RUN 落盘（runtime_state.last_run/{project}#{ep}） |
| 3 | 进度真相丢失 → 用户 / 总控看到进度归零，人工再点一次「一键生产」 | job_state.py:21（无落盘）+ 82 处裸写 | §4.2 铁律 1 + §4.3 对账回填 generation_state |
| 4 | ComfyUI 提交重复（prompt_id 台账未覆盖的路径） | comfyui_job_store 只覆盖 H3 序列（:1-33 自述）；分镜 / 资产图提交未见台账 | 分镜 / 资产 / 视频三段统一走 comfyui_job_store.find() / remember()（job_key = 项目+集+镜+工作流哈希） |

**风险**：对账逻辑若判错「已完成」，会把缺失产物当成功（比重复烧 GPU 更糟）。
**缓解**：判据只用「产物存在 + 非空 + 可解析」（is_unit_done(path, min_bytes)）+ 一次轻量 probe（分镜图查文件、视频查 ffprobe 时长>0）；对账**只做降级决策（少跑）而绝不删除任何产物**；对账结果全量打日志并进 /api/status，可人工核对。

**验证**：离线夹具（在测试项目上构造「running + 部分单元完成」的 DB 行与产物）+ 单测断言：对账后 status=done 的任务数 = 产物完整的任务数；pytest tests/test_stale_deliverable.py tests/test_recompose_closure.py -q。
