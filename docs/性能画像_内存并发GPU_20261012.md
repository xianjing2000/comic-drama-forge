## 2. 当前最大的 3 个瓶颈（点名到进程/阶段/参数）

### 瓶颈 1｜内存耗尽 → 三级换页（进程：ComfyUI pid 9876；阶段：分镜/视频出图）

- 证据：
  - ComfyUI private 峰值 **23730 MB**、WorkingSet 峰值 **11929 MB**；
    系统 Commit 峰值 **49.6 GB** > 物理 31.43 GB；可用物理内存最低 **3.7 GB**；
    Memory Compression **1.19 GB**；pagefile 峰值 **51.83 GB**。
  - 健康 GPU 态 84–112 W；模型换入瞬间掉到 **24.8 W**（util 85 %）。
    用户故障态 **util 100 % / 32 W / 2 分钟一步**是同一根因的极端表现。
  - 产物速率曲线：内存耗尽窗口 **86 分钟才出 1 镜**，重启释放后 3–6 分钟/镜。
- 点名参数：ComfyUI `--lowvram --reserve-vram 1 --disable-pinned-memory`（把权重堆在系统 RAM 而非 VRAM）；
  `TASK_QUEUE_CONCURRENCY=1`（GPU 并发 1，无本地并行能力可换时间）。
- 影响：这是**唯一会把整条流水线拖到「几乎停摆」的瓶颈**（其余是线性放大）。

### 瓶颈 2｜「提示词预检」阶段内嵌 LLM 增强调用（阶段：分镜前置段；进程：serve.py 调用 wb2api 7863）

- 证据（n=365）：`[分镜计时] … 提示词预检=X s` median **56.1 s**、mean 60.7 s、max **359.7 s**；
  同一条日志里 `参考图分配+归一=0.0s 身份基准网格=0.0s LLM九宫格规划+build提示词=13.9s`
  ——**预检独占前置段的 42 %，是前置段里最大单项**。
- 根因点名：`app/prompt_qc.py:_preflight_uncached()` 第 1523–1540 行
  在**确定性检查之前**调用 `prompt_enhance.enhance_prompt()`（LLM 调用），
  而 `prompt_enhance.py` 用 `timeout=PROMPT_ENHANCE_TIMEOUT_SEC`；
  `config.py:1339 PROMPT_ENHANCE_TIMEOUT_SEC = 90`。
  上游 7863 抖动时：**每次 90 s 超时 → 重试 → 每镜最多 270 s 纯等待**。
- 佐证：日志中 `Read timed out (read timeout=90)` **436 条**、
  `LLM 请求瞬时失败` **340 条**（几乎全部来自这一层）；且日志反复出现
  `[提示词增强] 本次不增强`——**付了 56 s 的账，却常常什么都没改**。
- 影响：46 镜 × 56 s 约 **43 分钟/集**的净浪费，且它已经把预取机制反噬
  （前置段 > GPU 段 → 预取命中也没用）。

### 瓶颈 3｜3D 站位基准图「必然超时再降级」（阶段：分镜前置段；进程：te_3d_render 无头浏览器）

## 4. 「必须加内存 / 换硬件」的阈值判据

### 4.1 加内存（RAM）判据

**立刻加（必须）**——满足任一条：

1. **可用物理内存连续 10 分钟 < 6 GB** 且 GPU 处于 UTIL>90 %；
   实测本机在分镜高峰期已到 **3.7 GB**（p10 4.2 GB），距 6 GB 判据**已经越线**。
2. **Commit 总量 > 物理内存 × 1.4**（即 > 44 GB）；实测峰值 **49.6 GB**（1.58×）——**已越线**。
3. `Memory Compression` 进程 > 1 GB 且 pagefile 峰值使用 > 物理内存（实测 51.83 GB > 31.43 GB）——**已越线**。
4. 视频阶段（尚未采样）一旦出现 19.5 GB 的 H3 权重 + 14.6 GB 文本编码器的加载，
   按当前口径**必然**触发 1–3。

**结论：本机 31.43 GB 对「分镜（6.8 GB 模型）+ 视频（19.5 GB 模型）」双阶段流水线是不够的。**
建议：
- **最低加装到 64 GB**（此时 Commit 峰值 49.6 GB 有约 14 GB 余量）；
- **推荐 96 GB**（可让 19.5 GB 模型 + 14.6 GB 编码器同时驻留 + 系统/前端余量）；
- 同时把 pagefile 固定到 **≥ 96 GB**（当前 78 GB，峰值已用到 51.83 GB）。

### 4.2 换 GPU 判据（显存是硬墙）

满足任一条即应换 **≥24 GB 显存**（RTX 4090/5090 级）：

1. **VRAM 峰值占用 > 总显存 × 85 %**；实测峰值 **6860 / 8151 MiB = 84 %**——**已达边缘**。
2. 出现「util > 90 % 但 power < 额定 40 %」的持续态：
   实测加载抖动样本 **util 85 % / 24.8 W**、用户故障态 **util 100 % / 32 W**；
   这是**显存/内存带宽被搬运卡住**而非算力不足的指纹。
3. 视频阶段模型加载时 `--lowvram` 下无法把 19.5 GB 权重切成 ≤6.8 GB 工作集跑完
   （表现为「分段超时 900 s」或 `comfyui_client` 心跳重启 ComfyUI）。

### 4.3 只靠参数优化的「天花板」

- ② + ① 能把**分镜单镜**从 343.6 s 压到约 230–290 s（省 16–33 %），
  但**改变不了**「可用内存 3.7 GB / Commit 49.6 GB」这个物理事实；
- 分镜阶段每集仍需约 3–4 小时，视频阶段在 8 GB 显存上仍有 OOM 与 900 s 段超时风险；
- 因此：**参数优化是"止血"，加内存（64–96 GB）才是"治好"**，换显卡是视频阶段规模化的前提。

nvidia-smi --query-gpu=index,name,memory.total,memory.used,utilization.gpu,power.draw,temperature.gpu,clocks.current.sm --format=csv
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv

# 系统内存 / Commit / 页文件
Get-CimInstance Win32_OperatingSystem | Select @{n='TotalGB';e={[math]::Round($_.TotalVisibleMemorySize/1MB,2)}},@{n='FreeGB';e={[math]::Round($_.FreePhysicalMemory/1MB,2)}}
Get-CimInstance Win32_PageFileUsage | Select Name,@{n='PeakGB';e={[math]::Round($_.PeakUsage/1024,2)}}

# ComfyUI 进程内存
Get-Process -Id 9876 | Select Id,@{n='WS_MB';e={[math]::Round($_.WorkingSet64/1MB,1)}},@{n='PrivMB';e={[math]::Round($_.PrivateMemorySize64/1MB,1)}}

# 生产（只读）：GPU 闸门 + 并发
Invoke-WebRequest http://127.0.0.1:5211/api/status -UseBasicParsing
