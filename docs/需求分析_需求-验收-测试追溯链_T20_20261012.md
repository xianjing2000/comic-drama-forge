## 4. 需求冲突与取舍

| # | 冲突 | 现状 | 建议取舍与理由 |
|---|---|---|---|
| C1 | **提速 vs 不降质检** | 2026-10-08 用户拍板「软放行 A 方案」：不合格只记录仍入库（storyboard_helpers.py:1510-1518）。代价=37% 镜不合格却显示成功 | 不要用「把 accept 改 True」抹平。改为**分层表达**：产物放行（不阻塞整集）+ 判定保持不达标 + 交付面红标 + 不计入 success_count。理由：用户要的是「不被 VLM 双标卡死整集」，不是「看不到问题」；当前做法把质量债藏进了交付面（manifest 46/46/0）。 |
| C2 | **参考图动态少量 vs 角色一致性** | 分配已动态（均值 2.87 张），但 45/46 镜无身份声明；cap ≤8（qc_helpers.py:496） | 先保证**每出场角色 1 张身份锚点 + 显式 imageN 声明**，场景/道具往后排；群像类角色（crowd）走文字锁定（已有四档分级：17075a7/3ee96e0）。理由：官方协议要求引用图与 imageN 编号一一对应，「有图无声明」等于把参考图当噪声；一致性缺陷（consistency）在缺陷库中占比最高。 |
| C3 | **段级返工(seg) vs 场级重做(scene)** | 默认按场次（MJSCXT_VIDEO_PER_SCENE=1）与 seg 段盘互斥；返工重拼只在整集模式有效 | 推荐**给按场次模式补一张 scene_map.json（scene→shot 列表）**，用 rework/shot_NN.mp4 重建受影响的 scene_NN.mp4 再 concat。理由：切回整集一次提交与「省 GPU/断点续跑」（video_helpers.py:1564-1568）直接冲突，而按场次是 2026-10-03 的用户决策；补映射 = 复用已有 rework 语义，改动面最小。 |
| C4 | **预检缓存(提速) vs 判定安全** | key 只有 8 个 ctx 字段（prompt_qc.py:1400-1428），而判据实读 17 个（t13） | 短期：key 加前缀版本号（模板/判据变更即整体失效）；中期：把 ctx 键集合从 prompt_enhance._CTX_KEYS 收敛为「判据真正读取的字段」。理由：命中即返回旧结论 = 新输入拿旧判决，属于「静默降级」。 |
| C5 | **不中断生产 vs 修复即时生效** | 同步层一致，但进程内代码停在启动时刻（13:17:33） | 增加只读的「代码指纹 vs 进程启动时间」健康检查 + 界面提示「有 N 个文件晚于进程启动，需重启才生效」；**不自动重启**。理由：本轮 T18/t19 的修复都无法自证生效，验证成本被推给下游。 |
| C6 | **面板雷同必须拦住 vs 整集不能停** | T18 恢复「面板雷同不软放行」= 回到重跑；而重跑成本是 GPU 分钟级 | 建议「面板雷同」单独走**降级放行 + 强制下一轮换机位条款**（不进正式交付、但对整集不阻塞），并原子化重跑预算。理由：直接把面板雷同并回硬阻断，会把 46 镜里 17 镜全部推回重跑（约 37% 产能），与「生产不能停」冲突。 |
