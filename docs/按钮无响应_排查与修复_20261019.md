# 前端按钮「点了没反应」——排查与修复（2026-10-19）

## 症状
桌面应用页面能打开、数据能显示、AI 对话能用，但「暂停托管」等按钮点下去**没有任何反应**，
也没有报错提示。截图里生产停在「分镜 3/7 · 已 4 分钟未推进」。

## 根因（已复现）
1. 前端 `api/client.ts` 的 `request()` 给**所有**非 FormData 请求都加
   `Content-Type: application/json`；
2. 但有 **6 个 POST 没有 body**：`autopilot/pause`、`autopilot/resume`、
   `qc/config/clear`、`qc/config/reset-endpoint`、`qc/config/sync-from-ai`、
   `autopilot/plan-from-settings/...`；
3. 后端普遍写 `data = request.json or {}`。**Flask 3** 里：
   - JSON 头 + 空 body → **400**（`Failed to decode JSON object`）
   - 无 JSON 头 → **415**（`Unsupported Media Type`）
   `or {}` 兜不住异常，接口直接 4xx；
4. 前端这些控制按钮又是 `catch { /* 静默 */ }` → **用户看到的只有"没反应"**。

> 这是升级到 Flask 3 后才暴露的潜伏 bug：Flask 2.x 的 `request.json` 失败时返回 None，
> `or {}` 恰好能兜住；3.x 改成抛异常。全仓 **63 处**都用了这种写法。

## 修复
| 侧 | 改动 |
|---|---|
| 后端 | `app/**` 29 个文件、**63 处** `request.json or {}` → `(request.get_json(silent=True) or {})`（与 `shared_web._body()` 的既有约定一致） |
| 前端 | `request()` 对**无 body 的 POST/PUT/PATCH 自动补 `body:'{}'`**，从源头避免空 body |
| 前端 | 「暂停/恢复托管」的静默 catch 改为 `toast.error(...)` —— 再失败会直接说明原因 |
| 产物 | `vite build` 重新生成 `app/static`（新 JS `index-CKkJogD_.js`），并用 `sync_assets --dir static` 同步进 Electron 打包源 |

## 验证（VM 实测）
- `POST /api/autopilot/pause`：**无 body / JSON 头空 body / 正常 JSON** 三种形态全部 **200**
  （修复前分别是 415 / 400 / 200）。
- 同批验证 `/api/autopilot/resume`、`/api/qc/config/clear`、`/api/qc/config/sync-from-ai` 均 200。
- `tsc --noEmit` 0 error；`vite build` 成功；`compileall app` 通过；`check_app_sync` 0 个目标不一致。

## 生效步骤（必须重启）
1. `python tools/sync_copies.py --apply` —— 同步 .py（含安装区与运行镜像；本环境只能同步到 Electron 打包源）
2. `python tools/sync_assets.py --dir static --apply` —— **`app/static` 不在 sync_copies 覆盖内**，
   桌面版必须单独同步前端产物，否则界面还是旧的（按钮能点，但没有新的 toast）
3. **重启桌面应用/后端**（进程不热加载）

## 如果重启后仍有个别按钮没反应
现在会弹出 toast 写明失败原因。把 toast 文案（或 DevTools Console / Network 里的状态码）
发来即可定位。排查顺序：① 请求有没有发出；② 状态码（400/415 = body/content-type，
404 = 后端版本旧，500 = 后端异常）；③ 前端是不是又静默 catch 了。

## 另一个独立问题：生产停在 3/7「4 分钟未推进」
这不是按钮问题。暂停修复后，若生产仍长时间不动，需要看后端日志里该镜是否卡在：
ComfyUI 提交/等待、LLM 预检、或质检重试循环。`/api/autopilot/status` 的
`current.step_stalled_sec` 会给出停滞秒数；`output`/数据目录下的 `logs` 有对应任务日志。

## 第二轮：全量核对（2026-10-19 晚，用户要求「别再口头说没问题」）

### 新增两个**可重复执行**的门禁工具
- `tools/check_api_contract.py`：把前端 **118 处调用**（`request()`/直接 `fetch`）与后端
  **232 条路由**逐条比对，查「路径不存在 / 方法不匹配 / 无 body 的写请求」。
  修复后：**✓ 0 缺失、✓ 0 方法不匹配**。
- `tools/check_routes_smoke.py`：把后端 **130 条 GET 路由**逐个真调用（4s 超时），抓 5xx / 卡死。
  修复后：**✓ 无 5xx、✓ 无超时**。

### 又抓到一个「全站卡死」的根因：历史计划目录拖垮轮询
- **现象**：`/api/autopilot/status` 单次 **14.5 秒**、`/plans` 6.9 秒、`/deliverables` 4.0 秒；
  工作台每 **3 秒**轮询一次，waitress 只有 8 个线程 → 慢请求把线程占满 →
  点击、暂停、切页全部排队无响应。
- **根因**：`output/autopilot/` 里有 **703 个历史/测试计划目录**，真实项目只有 1 个。
  `list_plans()` 对每个目录 `get_plan()` 读文件；`list_deliverables()` 对每个目录
  `read_json_strict`；`read_history()` 扫全部历史 jsonl。
- **修复**：
  1. `autopilot._output_project_keys()`：**一次性 listdir** 7 个产物父目录 + 10s 缓存，
     得到「仍有产物痕迹的项目集合」，与目录数无关；
  2. `list_plans()` 用 `scandir + DirEntry.is_dir()`（避免 700 次 `isdir` 系统调用），
     跳过注册表与产物里都不存在的历史目录；
  3. `read_history()` / `pipeline.list_deliverables()` 同样只统计仍存在的项目。
- **实测**：status **14.5s → 0.068s**；plans 6.9s → 0.028s；deliverables 4.0s → 0.033s；
  exceptions 8.1s → 0.035s；failure_summary 7.8s → 0.032s。
