### P0-1 图片质检主路径必抛 TypeError（已入库）

**位置**：`app/qc_client.py:2142`（HEAD 中的行号为 `2126`）
**函数**：`check_image()`

**缺陷代码**：

```
if ref_images and cfg.get("image_ref_compare",
"image_blocking_ref_compare", True):
```

`dict.get()` 最多只接受 2 个位置参数，此处传了 3 个。

**实测复现**（本地实跑，非推断）：

```

...

    if ref_images and cfg.get("image_ref_compare",

```

测试前 8 项（`build_ref_consistency_note` 段落生成）全 PASS，进入第 2 组「check_image 带参考图 → 一并送检」即崩溃。

**触发条件**：`ref_images` 为**非空**即抛（Python 短路求值，`ref_images` 为假时不会走到 `cfg.get`）。

**生产触发路径**（三处均真实传参，故为 live 缺陷而非死代码）：

- `app/app.py:2471` — 分镜图质检，`ref_images=_qc_ref_images(...)`
- `app/app.py:6068` — 关键帧/资产质检链路
- `app/app.py:10279` — 质检复检接口

**影响面**：分镜图质检的核心价值就是「把生成时用的角色/物品/场景设定图一并送检做一致性核对」。因此只要项目里存在角色设定图（**绝大多数项目的常态**），该调用必然抛异常。由于质检链路对回调异常采取 fail-closed（判不通过）策略，结果是**每张分镜都被判不通过**，反复重试后仍不通过 → 分镜链路实质卡死。

**引入点定位**：

- 基线 `3f0dacc:1661` 为正确写法：`cfg.get("image_ref_compare", True)`
- 基线全文件**不存在** `image_blocking_ref_compare` 这个键（计数 0）
- `b9bb9af` 同时引入「新键 `image_blocking_ref_compare`」与「三参 `dict.get`」——属**新增回落键时写坏了调用形式**

**修复方案（二选一）**：

- 最小修复（推荐，恢复原语义）：`if ref_images and cfg.get("image_ref_compare", True):`
- 若确实想保留新键做回落：`cfg.get("image_ref_compare", cfg.get("image_blocking_ref_compare", True))`

**顺带发现（同批接线未完成）**：新键 `image_blocking_ref_compare` 的全仓引用只有 6 处——`755` / `798` / `1025` / `1139`（登记与归一）、`2130`（**另一条独立用途**：控制 3D 基准图「文字规格」是否入质检提示词，默认 `False`）、`2143`（本缺陷处）。也就是说，这个新键**并没有形成一条独立的图片参考图比对开关**，它出现在此处纯属误写。修复时不应顺手把它接成新语义，否则会与 `:2130` 的用途混淆。

## 五、P2 中危（4 条）

### P2-1 剧本 QC 时长口径自相矛盾 + 下限校验形同虚设

**位置**：`app/qc_client.py:3605-3606`（常量）与 `:663`（提示词）

**事实**：

- `b9bb9af` 把常量从硬编码改为接 config 单一事实源，现在是：
  - `SHOT_DURATION_MIN_OK = config.SHOT_DURATION_MIN`（= 2.0）
  - `SHOT_DURATION_MAX_OK = config.SHOT_DURATION_MAX`（= 8.0）
  - 该处注释明确写着「已按参考片重标定到 1.5~8 秒，**故这里必须跟着 config 走**」——接线方向是对的
- **但**送给 QC 大模型的 `DEFAULT_SCRIPT_PROMPT` 规则 15（`:663`）**仍写「每个镜头时长应在 3-12 秒范围内」**，未同步更新
- 基线 `3f0dacc` 此处为硬编码 `3.0 / 12.0`，注释写「与 novel_to_script 对齐（3~12 秒）」——说明「3-12」是旧口径的遗留

**实测证据（三处断言转红）**：

- `verify_shot_segment_motion.py`：82 PASS / **1 FAIL**
  - 失败项：`E5 剧本QC时长口径仍为 3-12 秒（不与生成期 4 秒混用）max_ok=8.0`
  - 该断言同时校验「提示词里含『3-12 秒范围内』」与「常量 == 12.0」——**它编码的不变量正是「提示词与常量必须一致」**，因此这不是陈旧测试，而是**真实反映了口径矛盾**
- `verify_qc_memory.py`：160 项 / PASS 157 / **FAIL 3**，其中 2 项同源：
  - `单镜时长阈值与生成端对齐（3~12）`
  - `0.5 秒镜头仍报「过短」`

**第二重缺陷（更隐蔽）**：下限判据为 `duration < SHOT_DURATION_MIN_OK - SHOT_DURATION_TOLERANCE`，而 `SHOT_DURATION_TOLERANCE = 2.0` 未随 MIN 一起重定标：

- 旧：`3.0 − 2.0 = 1.0` → 短于 1.0 秒才会报警（有效）
- 新：`2.0 − 2.0 = 0.0` → **任何非负时长都不报警**，单镜「过短」校验彻底失效（`0.5 秒镜头仍报「过短」` 实测 FAIL 即为此）

**影响面**：① 质检大模型得到「3-12 秒合规」的指令，而确定性校验按「2~8（+2 容差）」判定 → 模型可能放过 9–10 秒镜头、或误判 2.5 秒镜头为过短，**同一份剧本出现两套互相打架的判定**；② 「过短」这条规则事实上已成死代码，静默失效。

**修复建议**：

1. **提示词的时长区间改为由常量生成**（如占位符替换或 f-string），从根上消除再次漂移的可能——与本项目既有教训「任何追加式装饰都要与实现同源」一致
2. 重新定标 `SHOT_DURATION_TOLERANCE`（例如 0.5），或显式说明「静默镜基准 0.6s 合法，故下限不设卡」，避免留下一条**看起来在跑、实际永不触发**的规则
3. 同批更新上述两个测试文件的期望值（保持「提示词与常量一致」这条不变量的断言结构）

### P2-3 跨集衔接 state 读错集号（off-by-one）

**位置**：`app/app.py:7188`

**缺陷代码**：

```python
if _epn and int(_epn) > 1:
    from continuity import load_state as _load_ep_state
    _prev_ep_state = _load_ep_state(_cont_dir, project_name,
                                    int(_epn)) or {}
```

**判定依据（canonical 语义）**：

- `continuity.load_state(continuity_dir, project_key, episode_no)` 读的是**指定那一集**的 state（`continuity.py:860`）
- 同文件内的两处 canonical 调用都显式减 1 取上一集：`continuity.py:1343`、`continuity.py:1888` 均为 `load_state(continuity_dir, project_key, int(episode_no) - 1)`
- 本处变量名为 `_prev_ep_state`（上集），紧邻的异常日志也写「**上集** state 加载失败（按无上集处理）」——**命名与日志都表明意图是「取上集」，但传参未减 1**

**影响面**：第 2 集及以后，本应取第 N−1 集的 state，实际取了第 N 集自己的 state。首次运行第 N 集时，第 N 集 state 尚不存在 → `or {}` 静默退回「无上集」（fail-open，不崩）；但若第 N 集 state 已存在（重跑/续跑场景），就会把**本集**的 state 当作「上集」注入，用于首镜跨集衔接 → **一致性锚点是错的，且完全静默**。

**修复方案**：`int(_epn) - 1`（与 canonical 一致）。
