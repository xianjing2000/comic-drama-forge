### 结论：**不是「全部用同一个」，而是两个不同文件 —— 且只有一个是活的**

| 大小 | 1,956,193,000 B | 1,956,171,984 B |

### 关键判据

1. **两个文件内容确实不同**：A ⊃ B（A 独有 208 键、B 独有 **0** 键），
   共有 416 键**形状 100% 一致（0 处差异）** → **A 是在 B 基础上补了 alpha 元数据的「再转换版」**
   （scale 0.125 ÷ 2 = 0.0625，与 alpha/rank = 8/128 = 0.0625 吻合）。
   **不是同一次转换的不同路径前缀，权重是独立转换的。**
2. **只有通道 A 真正参与成片**：`H3_ENABLE_REFINE = False`（`config.py:660`，2026-09-28 拍板）
   → 二采链（`54/55/62/63/33/38`）**根本不执行** → **通道 B 的 LoRA 是死代码，对成片零影响**。
3. **两个 LoRA 槽位都没有被覆盖**：`output/comfyui_models.json` 只写了
   `{"unet_main": "minimax-h3\\minimax_h3_ref2va_pruned_int8_convrot.safetensors"}`，
   两个 LoRA 槽位无值 → **完全沿用模板原值**（即上表两个不同文件）。
4. **截图里该 LoRA 被跳过是正常现象**：用户选的任务类型是 `r2v`，
   该链路本就不挂 LoRA → 节点未参与执行，**不是故障**。
5. **LoRA 从未被改动过**：比对 git 三个历史版本（`943af3a`/`f832e24`/`ce20c0b`）的
   LoRA 节点值，**三版完全一致**。

## 二、本轮修掉的 4 项遗留

### ① ⭐⭐ `verify_storyboard_ref_canvas.py` G2「存量失败」——**不是假红，是真缺陷**

**现象**：G2 断言所有参考图都是 `1216×672`，实测 `[(1216,672),(1216,684),(1216,672)]`。

**根因（跨模块画幅语义冲突）**：

| 环节 | 值 | 语义 |
|---|---|---|
| `style_kit.resolve()["ratio"]` | `(16, 9)` | **16:9 横屏**，`aspect_size` → `1216×672` ✅ |
| `app.py:6345` 手工拼串传入 | `"16:9"` | 同上 |
| `te_3d_director._ASPECT_RATIO["16:9"]` | `(16,9)` 被当 **(宽比, 高比)** | `h = 1216 × 9/16 = ` **684** ❌ |

→ **同一个「16:9」，两个模块解出两个像素**。

**危害**：3D 站位基准图是 `<image1>` **画布定义者**（分镜图画幅继承第一张参考图），
所以它以 684 高定画布 → 分镜图继承错误画幅，与全局 672 打架。

**⚠️ 重要澄清**：`plan_pixel_size` **本身没有错** —— 守卫断言
`9:16 → 高/宽 ≈ 16/9`（竖屏）一直是**通过**的。错的只是**调用方传参语义**。
（曾一度想「把 `bh/bw` 翻过来」，那会**破坏竖屏**，已否决。）

**修法（三处，均不动 `plan_pixel_size`）**：
1. `app/te_3d_director.py` 新增 **`fit_pixel_size(target_size, max_width)`** ——
   **按目标像素**反推渲染尺寸，彻底绕开比例字符串的双语义（唯一无歧义口径）。
2. `build_render_plan(..., target_size=None)` 与 `render_blocking(..., target_size=None)` 接上该参数。
3. `app.py` 传 `target_size=_sb_size`；**并在 3D 基准图 `insert(0, …)` 之后补一次
   `_unify_ref_canvas`** —— 原先它在归一**之后**插入，**躲过了归一**（顺序隐患）。

**结果**：G2 → `[(1216,672)×3]` 转绿，**38 PASS / 0 FAIL**（原 37 / 1）。

### ② `_ATTEMPTS` 落盘（`max_episode_attempts=2` 原本形同虚设）

**问题**：`autopilot._ATTEMPTS` 原为**纯内存** → 守护进程一重启就清零 →
「连续 2 次失败即挂起」的机制**在重启面前完全失效** → 实测出现
「分镜判失败 → 每轮全量重跑 6 镜」的死循环，**白烧 GPU 约 40 分钟**。

**修法**：新增 6 个函数，范式与既有 `last_run` 完全同构
（`atomic_write_json` 落盘 + 读盘回落 + **失败只告警、绝不阻断生产**）：
`_attempts_path` / `_save_attempts` / `_load_attempts` / `_attempts_get` / `_bump_attempt` / `_reset_attempt`。

**两个关键细节**：
- ⭐ `_load_attempts` **必须把键转 `int`**：JSON 的键会全部变成字符串，
  不转则与 `_ATTEMPTS[ep]` 的 int 键**永远对不上** → 计数永远读不到 0 以外的值（**静默失效**）。
- ⭐ `_attempts_get` 采用**懒加载**：内存里没有该项目的键时才从盘载入
  （否则运行期新建/发现的项目仍会漏）。
- `purge_project` 同步删除盘上 `attempts.json`（否则同名项目重建会带着旧计数起步 → 一失败就立刻挂起）。

**守卫**：`.workbuddy/test/verify_attempts_persist.py`（新增，**11 项全绿**）——
含「写盘生效」「模拟重启后读回」「键为 int」「清零也落盘」「源码契约」五段。
